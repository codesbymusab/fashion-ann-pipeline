Abstract—Managing machine learning pipelines requires decoupled versioning paradigms: source code is tracked via directed acyclic graphs in Git, while large-scale binary artifacts (raw datasets, transformed tensors, model weights) must be tracked via content-addressable storage to prevent repository bloating. This report presents an empirical study and end-to-end implementation of an MLOps pipeline on the Fashion-MNIST benchmark utilizing Git, Data Version Control (DVC), and Google Drive. We analyze advanced Git workflows including stash recovery, atomic file renames, non-fast-forward hotfix integration, and rebase conflict resolution. Next, we construct a 4-stage modular pipeline governed by dvc.yaml and params.yaml, demonstrating automated reproducibility and selective stage-skipping across hyperparameter modifications (dense units: 128 vs 256). Finally, we simulate a distributed team collaboration scenario, reproducing the concurrent emergence of a Python textual code conflict and an md5 hash collision in dvc.lock, followed by an authoritative reconciliation strategy. All metrics, audits, and reproducibility proofs are verified.
Keywords: Machine Learning Operations (MLOps), Git, Data Version Control (DVC), Google Drive Remote, Artificial Neural Networks (ANN), Data Provenance, Merge Conflict Reconciliation.

1. Introduction & MethodologySection I

In production MLOps architectures, code and data evolve along distinct lifecycles. Standard software engineering version control tools are optimized for delta-compressed UTF-8 source files. Storing high-dimensional numerical matrices (such as Fashion-MNIST's 60,000 image arrays) directly in Git causes severe repository bloat and slows down distributed operations. DVC addresses this by generating lightweight cryptographic hash pointers (md5) tracked in Git, while delegating heavy payloads to remote cloud storage. In this work, the architecture is realized in fashion-ann-pipeline.

2.4 Relative Diff Analysis: Two-Dot vs Three-Dot Syntax (A4)

Figure 3: Unstaged, staged, and relative branch comparisons (A4).

Two-Dot (main..dev) vs Three-Dot (main...dev) Mathematical Semantics:

• Two-dot diff (git diff main..dev): Directly computes the symmetric difference between the branch tips. It incorporates all disparate commits, meaning changes committed exclusively to main appear as reverse/negative diffs in dev.

• Three-dot diff (git diff main...dev): Computes the merge-base (common ancestor) between main and dev, comparing dev exclusively against this ancestor. It strictly isolates the feature contributions of dev, filtering out unrelated upstream commits on main.

2.6 Reset Mechanics: Soft vs Hard State Recovery (A7)

Figure 5: Soft reset (staged on disk) vs hard reset (purged working tree) (A7).

Operational Comparison: --soft rewinds only the branch pointer (HEAD); modifications remain staged in the index and preserved on disk for commit consolidation. --hard rewinds HEAD, index, and working tree synchronously, permanently expunging changes from disk.

3. Part B: Fashion-MNIST ANN PipelineSection III

A decoupled 4-stage pipeline was engineered to process Fashion-MNIST (60,000 train, 10,000 test arrays):

• B1 Ingestion (src/prepare.py): Ingests dataset via keras.datasets; writes deterministic .npy files to data/raw/ to ensure cryptographic hash stability.

• B2 Preprocessing (src/preprocess.py): Scales pixels to [0, 1], carves a 10% stratified validation split, and outputs 6 array files to data/processed/.

• B3 Neural Modeling (src/train.py): Builds sequential ANN (Flatten → Dense(ReLU) → Dropout(0.2) → Dense(10, Softmax)). Logs history to history.csv, saves weights to models/model.h5.

• B4 Evaluation (src/evaluate.py): Computes test metrics, serializes metrics.json, and renders confusion_matrix.png.

Empirical Convergence: Baseline training across 10 epochs converged at 89.02% validation accuracy and 0.3064 validation loss.

6. Part E: Collaboration Simulation & Dual Conflict ResolutionSection VI

6.1 Divergent Preprocessing Branches (E1, E2)

Following merge of dev into main, branch teammate-sim implemented Fashion-MNIST standardization: (x / 255.0 - 0.2860) / 0.3530, regenerated processed data via dvc repro preprocess, and pushed to Drive. Concurrently on main, centering was implemented: (x / 255.0) - 0.5, regenerated, and pushed.

6.2 Dual Code & Data Pointer Conflict (E3)

Merging teammate-sim triggered two distinct collisions: a text collision in src/preprocess.py and a hash directory collision in dvc.lock for data/processed (Figure 9).

Figure 9: Dual merge collision in code and dvc.lock, reconciliation, and regeneration (Part E).

6.3 Authoritative Resolution & Reproducibility (E4, E5)

1. Code Reconciliation: Unified both branches by preserving the initial [0, 1] scaling and standardizing via empirical constants (mean=0.2860, std=0.3530).

2. Data Lock Resolution: Because the unified code yields a novel 3rd dataset version, conflict markers were cleared with git checkout --ours dvc.lock, synced via dvc checkout, and regenerated from source via dvc repro (final accuracy: 87.15%).

3. Reproducibility Verification: Re-executing dvc repro immediately after merge confirmed all stages print "didn't change, skipping".

8. ConclusionSection VIII

This implementation proves the viability of combining Git for semantic code deltas and DVC for content-addressed array caching. The automated pipeline ensures full tracking provenance, eliminating redundant computations and establishing deterministic multi-developer collaboration in MLOps.
